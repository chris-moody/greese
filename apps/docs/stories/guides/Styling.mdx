# Styling components

**Guides/Theming** changes the design tokens every component reads. This guide
covers everything past tokens: a component's classes, parts and variables;
overriding them in CSS; the **SCSS kit**, which writes those overrides for you
at build time; and theme-wide motion. [Guides/SCSS themes](?path=/docs/guides-scss-themes--docs) puts it
together: exporting a theme from **Theme Studio** and keeping it in your source
as the theme layout, a file at a time.

Every component's docs page, parts like AccordionItem and TableRow included,
also ends with a **Styling** section: its anatomy (its first example, every
element outlined and labelled with its classes), then tables of what it
renders: its parts (root, parts, modifiers and state attributes, each with the
class it sits in and what it styles), its responsive props, and its own
variables (default, type, and the properties they end up in). Then its items,
the components it's built on (an AccordionItem is a Collapsible), and
override examples written for it.

## Choosing a level

Use the first level that does the job:

| Level                      | For                                               | Example                                                |
| -------------------------- | ------------------------------------------------- | ------------------------------------------------------ |
| Props                      | What the API offers                               | `<Button variant="outline" tone="negative">`           |
| `className`, `style`       | One instance                                      | `<Card className="pricing-card">`                      |
| Component variables        | A component's knobs, anywhere in the tree         | `.sidebar { --greese-button-height: 2rem }`            |
| Tokens                     | The whole design (see Guides/Theming)             | `createTheme({ radius: { md: '12px' } })`              |
| CSS overrides              | Anything else, in your own stylesheet             | `.greese-Card { box-shadow: var(--greese-shadow-lg) }` |
| The SCSS kit, Theme Studio | A whole theme of overrides, checked at build time | `@include greese.component(Card) { … }`                |

## Class names

Every class is prefixed and never hashed, so it's safe to target:

| Kind     | Pattern                     | Example                                               |
| -------- | --------------------------- | ----------------------------------------------------- |
| Root     | `greese-<Name>`             | `.greese-Button`                                      |
| Part     | `greese-<Name>-<part>`      | `.greese-Button-icon`, `.greese-Dialog-title`         |
| Modifier | `greese-<Name>--<modifier>` | `.greese-Button--outline`, `.greese-Button--size-sm`  |
| State    | an attribute                | `.greese-Button[data-loading]`, `[aria-invalid=true]` |

Responsive props also add classes (`.greese-Stack--md-gap-2`). They're
generated per breakpoint and token, so don't target them; set the prop.

**Stability.** Root classes and documented variables are stable. Parts and
modifiers can change in a minor release, as markup does. If you target them
through the SCSS kit, a renamed part stops your build with an error instead
of silently not matching.

## Where overrides land: cascade layers

All greese ui CSS lives in cascade layers, in this order (later wins):

```css
@layer greese.reset, greese.tokens, greese.theme, greese.base,
       greese.components, greese.overrides, greese.utilities;
```

| Layer               | Holds                                                |
| ------------------- | ---------------------------------------------------- |
| `greese.theme`      | Token overrides: `createTheme`, the kit's `tokens()` |
| `greese.components` | The library's component styles                       |
| `greese.overrides`  | The kit's `component()` and `motion()` overrides     |
| `greese.utilities`  | Style props (`p={4}`) and the `greese` prop          |
| (unlayered)         | Your own CSS                                         |

So a kit override beats the component's own styles whatever their
specificity, but a style prop or a `greese` prop on one instance still beats
the override. Your unlayered CSS beats everything, without `!important`.

## Overriding in plain CSS

Write normal CSS against the classes. It's unlayered, so it wins:

```css
.greese-Card {
  box-shadow: var(--greese-shadow-lg);
}

.greese-Button--outline {
  border-width: 2px;
}

/* Variables restyle every variant at once: the soft, outline and ghost
   backgrounds are all mixed from the tone. */
.danger-zone .greese-Button {
  --greese-button-tone: var(--greese-color-negative);
  --greese-button-on-tone: var(--greese-color-negative-content);
}
```

Prefer variables to properties where a component has them: they survive
markup changes, and they cover states (hover, active) the component derives
from them.

## The SCSS kit

The kit is a Sass module for writing a theme as overrides that compile in
your build. You write names; it adds the `greese-` prefix and separators,
puts each override in the right layer, and **stops the build on a name the
library doesn't have**, listing the ones it does.

### Setup

Compile with Sass's `NodePackageImporter`, which resolves `pkg:` URLs
([Guides/SCSS themes](?path=/docs/guides-scss-themes--docs) shows the Vite config). Then, in a stylesheet
imported **after** greese ui's styles:

```scss
// theme.scss
@use 'pkg:@greese/ui/scss/kit' as greese;
```

Using the module emits nothing. Its mixins emit the CSS, plus the layer order
once, so the order holds whichever stylesheet loads first.

### Tokens

`tokens()` is the build-time `createTheme`. Groups and keys are kebab-case (or
camelCase); a color takes one value or a light/dark pair:

```scss
@include greese.tokens(
  (
    color: (
      primary: (
        light: #7c3aed,
        dark: #c4b5fd,
      ),
      primary-content: #fff,
    ),
    radius: (
      md: 12px,
    ),
    font: (
      body: (
        'Inter',
        system-ui,
        sans-serif,
      ),
    ),
  )
);
```

To add tokens the system doesn't have, name them in `$extend`, in the same
shape. Each becomes `--greese-<group>-<name>`, and `token()` and component
variables accept it from then on. A name that already exists, or a group
that doesn't, still stops the build:

```scss
@include greese.tokens(
  (),
  $extend: (
    color: (
      brand-ink: (
        light: #1b1340,
        dark: #e5defc,
      ),
    ),
    space: (
      9: 4rem,
    ),
    shadow: (
      glow: 0 0 12px rgb(124 58 237 / 0.4),
    )
  )
);

.my-banner {
  color: var(--greese-color-brand-ink); // from any CSS, after the built stylesheet
  margin-block: var(--greese-space-9);
}
```

A new `space` token is a variable only: the responsive prop classes
(`gap={9}`) come with the stylesheet's build, which knows `0`–`8`.

At the top level it overrides only what you pass, on the page, mirroring the
default selectors, so light, dark and nested schemes all work. Duration
overrides still collapse under reduced motion.

Calls add up. A second `tokens()` call for the same theme, or for the page,
writes only what it changes. Token groups can therefore live in files of their
own, and the result is the same as one call with everything merged:

```scss
@include greese.tokens($colors);
@include greese.tokens($radii); // the colors stay
```

### Components

```scss
@include greese.component(Button) {
  font-weight: 700; // .greese-Button

  @include greese.vars(
    (
      tone: greese.token(color, positive),
    )
  ); // --greese-button-tone

  @include greese.modifier(outline) {
    // .greese-Button--outline
    border-width: 2px;
  }

  @include greese.part(icon) {
    // .greese-Button .greese-Button-icon
    opacity: 0.8;
  }

  @include greese.hover {
    // only where hover exists
    translate: 0 -1px;
  }
}
```

| Kit API                                                                  | Gives                                                                                                                                                                        |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `component(Name) { … }`                                                  | `.greese-Name { … }` in `greese.overrides`                                                                                                                                   |
| `part(name) { … }`                                                       | `& .greese-Name-name`                                                                                                                                                        |
| `modifier(name) { … }`                                                   | `&.greese-Name--name`, or the enclosing part's modifier                                                                                                                      |
| `vars((name: value, …))`                                                 | Custom properties. Short names (`tone`), full names (`button-tone`) or tokens (`radius-md`, rescoped to the component). A `(light: …, dark: …)` value becomes `light-dark()` |
| `motion((…))`                                                            | Theme-wide motion for the component: see [below](#theme-wide-motion)                                                                                                         |
| `class(Name, $part, $modifier)`                                          | The selector string, for your own rules: `#{greese.class(Card)} > p`                                                                                                         |
| `token(group, key)`                                                      | `var(--greese-<group>-<key>)`, checked                                                                                                                                       |
| `variable(name)`                                                         | `var(--greese-<name>)` for a component variable, checked                                                                                                                     |
| `tokens((…))`, `motion-defaults((…))`, `theme(name) { … }`               | Token overrides, entrance tuning, a named theme                                                                                                                              |
| `keyframes(greese-float-up, (from: (…), to: (…)))`                       | Adds `@keyframes` of your own (utilities layer); a built-in effect's name is refused                                                                                         |
| `page-transitions(('.greese-Card': (exit: scale-out), 'header': still))` | Selector rules for page transitions: those elements get their own effects (or none) while a greese page change runs                                                          |
| `up`, `down`, `hover`, `focus-ring`, `touch-target`, `motion-safe`       | The library's own mixins                                                                                                                                                     |

Call the mixins at the top level of a stylesheet (or inside `theme()`), not
inside your own selectors.

`light-dark()` follows the nearest color scheme natively. If your build
targets browsers without it, Lightning CSS and others polyfill it in a way
that breaks nested schemes (ADR 0002); use a token there instead.

### Named themes

Inside `theme(name)`, `tokens()` declares a **complete** theme for
`data-greese-theme="name"`, exactly as `createTheme` does, and component and
motion overrides apply only inside it:

```scss
@include greese.theme(brand) {
  @include greese.tokens(
    (
      color: (
        primary: (
          light: #0f766e,
          dark: #5eead4,
        ),
      ),
    )
  );

  @include greese.component(Card) {
    border-radius: 0;
  }
}
```

Scope it with `ThemeProvider` by name. Its CSS is already in your bundle, so
the provider only stamps the attributes (and keeps nested schemes working):

```tsx
<ThemeProvider theme="brand">…</ThemeProvider>
```

Component overrides are descendant selectors, so a theme nested inside
`brand` still gets `brand`'s component overrides (tokens replace; overrides
add up). [Take them back](?path=/docs/guides-scss-themes--docs) where you don't want
them: Guides/SCSS themes, "Taking a theme's layers back".

`scope($name)` is `theme($name)` when there is a name, and the page when there
isn't (`null`, `false` or `''`), so one file serves either:

```scss
$theme: brand; // or null

@include greese.scope($theme) {
  @include greese.component(Card) {
    border-radius: 0;
  }
}
```

The theme layout keeps that name in `_settings.scss` (Guides/SCSS themes).

### Strict names

Unknown names are build errors:

```
Error: greese ui kit: `Button` has no part `icn`. Parts: icon.
```

To target a class this version doesn't know (a part from a newer release, say),
turn the check off: `@use 'pkg:@greese/ui/scss/kit' as greese with ($strict: false);`.

### The library's own mixins

The components are written with a handful of partials, and a theme can `@use`
them too, so styles copied from a component's source compile in your theme:

| Entry point                     | What's in it                                                                                              |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `pkg:@greese/ui/scss/mixins`    | `up`, `down`, `hover`, `focus-ring`, `touch-target`, `motion-safe`, `component-root`                      |
| `pkg:@greese/ui/scss/tones`     | `$tones` (each tone's color and content color) and `$brand`                                               |
| `pkg:@greese/ui/scss/floating`  | `surface`, `anchored`, `enter-exit`: what the overlays share                                              |
| `pkg:@greese/ui/scss/controls`  | `$sizes`, `frame`, `focused`, `no-zoom-font`: what the form controls share                                |
| `pkg:@greese/ui/scss/maps`      | the token maps (`$color`, `$scalars`, `$breakpoints`, `$typography`…)                                     |
| `pkg:@greese/ui/scss/utilities` | `classes()`: the [utility classes](?path=/docs/guides-utility-classes--docs), built with your breakpoints |

```scss
@use 'pkg:@greese/ui/scss/kit' as greese;
@use 'pkg:@greese/ui/scss/mixins';
@use 'pkg:@greese/ui/scss/floating';

@include greese.component(Popover) {
  @include floating.surface;

  @include mixins.up(md) {
    padding: greese.token(space, 6);
  }
}
```

They are the modules the library itself loads, so a build with its own
breakpoints (`@use 'pkg:@greese/ui/scss' with ($breakpoints: …)`) reaches
`mixins.up()` too. What writes a component's own class names (the
responsive-prop machinery, `tones.classes`) stays private.

Two more entry points write CSS, for a Sass build that picks its components:
`pkg:@greese/ui/scss/core` (the layer order, tokens and type system) and
`pkg:@greese/ui/scss/components/<Name>` (one component's own stylesheet):

```scss
@use 'pkg:@greese/ui/scss/config' with (
  $breakpoints: (
    xs: 0px,
    sm: 480px,
    md: 700px,
    lg: 1024px,
    xl: 1440px,
  )
);
@use 'pkg:@greese/ui/scss/core';
@use 'pkg:@greese/ui/scss/components/Stack';
@use 'pkg:@greese/ui/scss/components/Button';
```

A component built on others (a Dialog renders a Button) needs theirs too. To
replace a component's styles outright, leave its stylesheet out and write your
own `.greese-<Name>` rules in `@layer greese.components`.

## Theme-wide motion

`motion()` gives every instance of a component a default, in pure CSS: what
the `greese` prop does per instance, for all of them. It plays behind
`prefers-reduced-motion: no-preference`.

```scss
@include greese.component(Card) {
  @include greese.motion(
    (
      enter: fade-up,
      duration: 0.4s,
      distance: 1.5rem,
    )
  );
}

@include greese.component(Dialog) {
  @include greese.motion(
    (
      exit: scale-out,
    )
  );
}

@include greese.component(Switch) {
  // The component's own transitions: its duration and easing tokens.
  @include greese.motion(
    (
      durations: (
        fast: 80ms,
      ),
      easings: (
        standard: linear,
      ),
    )
  );
}

// Tunes every greese prop entrance, and the defaults above.
@include greese.motion-defaults(
  (
    duration: 0.3s,
    ease: out,
  )
);
```

| Option                                  | Does                                                                                                                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `enter`                                 | A preset played when it appears: `fade-in`, `fade-up`, `fade-down`, `fade-start`, `fade-end`, `scale-in`, `blur-in`, `slide-up`, `pop` |
| `keyframes`                             | Your own `@keyframes` name instead                                                                                                     |
| `exit`                                  | How an overlay leaves: `fade-out`, `fade-out-up`, `fade-out-down`, `scale-out`                                                         |
| `duration`, `delay`, `ease`, `distance` | Tune the entrance. `ease` is a name (`out`, `in-out`, …) or a `cubic-bezier()`                                                         |
| `durations`, `easings`                  | The component's transition speeds and curves, rescoping the tokens to it                                                               |

Per instance:

- an instance's own `greese` entrance **replaces** the default (it's in a later
  layer);
- its `duration`, `delay` and `ease` options **tune** the default;
- `style={{ animation: 'none' }}` turns it off for that instance.

Entrance presets need the Motion styles: they're in `styles.css`; with
per-component CSS, also import `@greese/react/css/Motion.css`.

Scroll reveals and hover, press and focus effects need the JavaScript
runtime, so they stay per instance, on the `greese` prop.

## Keeping a theme in your source

A theme written with the kit is best kept as **the theme layout**: a folder of
Sass modules, a file per component and per token group, which Theme Studio
exports and you maintain from then on. [Guides/SCSS themes](?path=/docs/guides-scss-themes--docs) covers it end
to end: exporting from Theme Studio, building it, every file and what it
holds, changing it, and taking a theme's layers back with `.greese-reset-*`
and `reset()`.
